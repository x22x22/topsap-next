# v1.3.2

发布日期：2026-11-06

## 概述

TopSAP Client v1.3.2 是 macOS 数据面修复版本。针对员工反馈的「路由注入全部失败」与网卡自检「接收方向」失败，本版确认并修复了两个 macOS 根因：其他 VPN / 官方客户端占用同一批资源路由，以及 utun 对端与资源路由网关误用本机 VIP。新增连接前路由冲突预检与接管确认、诊断页 utun 残留清理，并把 macOS utun 对端与路由网关修正为 VIP-1；自检读取路径改为系统主动发包验证。Windows 与 Linux 的连接、路由与数据面行为未改动。

## 新增

### macOS 路由冲突预检与接管

- 连接前读取 `netstat -rn -f inet`，按目标网段与前缀精确比对，提前发现被其他接口占用的路由
- 发现冲突时暂停连接并弹窗列出冲突接口、网关与网段；用户选择「接管并连接」后删除冲突路由再注入，取消或 120 秒超时则中止连接
- 弹窗明确提示：接管可能中断官方 TopSAP 或其他 VPN，断开后不会自动恢复
- `ok == 0` 时也把失败明细写入运行日志，不再只输出一句总错误

### macOS 诊断页 utun 残留清理

- 列出带 IPv4 地址的 utun：名称、`地址 → 对端`、MTU、关联路由数
- 当前连接使用的接口标记为「使用中」且不可清理；自检进行中拒绝清理
- 二次确认后执行 `ifconfig utunN down` 并删除剩余关联路由；接口仍存在时提示可能仍有进程持有隧道

### 异常退出定向清理自身 utun

- 会话标记额外记录本次创建的 utun 名称与 VIP
- 下次启动/连接前，仅当接口地址与记录完全一致时才关闭并清理该 utun，避免误伤同名接口

## 修复

### macOS utun 对端与路由网关

- 官方客户端实测 utun 形态为 `inet VIP --> VIP-1`，资源路由 Gateway 为 VIP-1；旧实现把本机 VIP 同时当作对端和网关
- 旧实现下 `route get` 回读能匹配接口，但系统流量不会真正投递到 utun，表现为自检接收方向超时、连接后内网可能不通
- 新增 `virtual_peer(vip, mask) = VIP-1`（校验网络地址/广播地址，`/31`、`/32` 特判）
- utun 配置改为 `ifconfig <if> inet VIP VIP-1 netmask ... up`，资源路由改为 `route -n add -net <dest> -netmask <mask> VIP-1`
- 删除路由时先按 VIP-1，再回退旧 VIP 形式，兼容历史残留
- `HELPER_VERSION` 升至 `1.2.4`，升级后首次启动会再次请求管理员授权

### macOS 自检接收方向

- 旧方案依赖向 utun 注入报文后由内核生成回包；在对端配置错误或存在残留路由时，路由回读通过但读路径实际不可用
- macOS 改为由系统执行 `ping -S <VIP> <测试目标>` 主动发包，读循环收到该 ICMP Echo 请求即证明「系统 → utun」读路径与测试路由生效
- 注入测试路由前先检查同前缀冲突，冲突时直接报出占用接口并跳过后续测试
- Windows / Linux 保持原有「注入报文并等待系统回包」的验证方式，行为不变

### 文案与测试数据

- 补齐路由冲突、utun 清理结果、连接阶段等新增文案的中英文词条
- 新增测试中的真实内网地址改为 RFC 5737 文档网段，不涉及运行时行为

## 安装

- Windows 安装包：`TopSAP Client_1.3.2_x64-setup.exe`，支持 `/S` 静默安装
- Windows 便携版：保留 `resources/wintun.dll` 相对路径，以管理员身份运行
- macOS：首次启动或 helper 版本升级后按提示重新授权 root helper；未签名与公证，首次打开需处理 Gatekeeper
- Linux：需 `sudo /usr/bin/topsap-client` 启动；普通用户双击会弹窗提示

## 已知限制

- macOS 修复需真机回归：确认 `ifconfig utunN` 显示 `inet VIP --> VIP-1`、自检接收方向通过、连接后资源路由 Gateway 为 VIP-1
- 若官方 TopSAP 守护进程仍在运行，接管删除的路由可能被重新写回；正确做法是先退出官方客户端
- 接管模式删除的是其他接口的现有路由，断开后不会自动恢复
- helper 版本升至 `1.2.4`，升级后首次启动需要重新授权
- 其余限制同 v1.3.1：仅支持 `ngvone` / `cipher_type=0` 网关；TUN / 透明代理无法使用系统代理绕过；英文模式下的网关动态 `ErrMsg` 仍可能显示中文原文
